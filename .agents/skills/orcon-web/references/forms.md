# Forms

Status: Accepted (2026-10-13)

This document defines how forms are built: React Hook Form with schemas generated from the API contract, field names that are JSON pointers so server errors land on the right field, messages from catalogs, and node configuration forms generated from connector manifests (ADR 0078). How a field, an error or a summary looks is defined by `orcon-ui` ([forms and errors](../../orcon-ui/references/components.md#forms-and-errors)). Rule IDs (`FM-…`) are stable.

Precedence: accepted ADRs > accepted `orcon-go` rules > `orcon-ui` rules for anything visual > this rulebook > reviewer preference.

## Schema and fields

- **FM-1** Forms use React Hook Form with `zodResolver(schema)`. The schema is the generated request schema from `@orcon/api-contract/zod`, extended only for UI-only rules; server fields are never redefined by hand.
- **FM-2** Each field sits in the `orcon-ui` `FormField` with `name` set to the JSON pointer of the request body field (`/name`, `/settings/timeout`), so server errors map to it ([forms and errors](../../orcon-ui/references/components.md#forms-and-errors)).

## Errors and messages

- **FM-3** On a `400`/`422` problem, the form passes it to `ProblemErrorsProvider`, calls `setError` for each pointer, renders `ErrorSummary` and moves focus to it; input is never cleared.
- **FM-4** Validation messages come from catalogs: `app/forms/zod-messages.ts` maps each Zod issue code to a message descriptor (`validation.<code>`); raw Zod messages are never shown. Catalog rules: [content and i18n](../../orcon-ui/references/content-and-i18n.md#strings).

## Behavior

- **FM-5** `mode: 'onTouched'`, re-validate on change; the submit button stays enabled for invalid input and errors appear on submit.
- **FM-6** Server data enters a form through `values` with `resetOptions: { keepDirtyValues: true }`; leaving a dirty form asks for confirmation (`useBlocker`).
- **FM-8** Secret inputs are write-only: never prefilled, never logged, never placed in the query cache.
- **FM-9** While a submit is pending, submitting again is disabled; retries rely on the SDK idempotency key.

## Node configuration forms

- **FM-7** Node configuration forms are generated by one renderer in `features/editor/forms/node-config/` from the connector manifest schema (SPEC-003): field kind from type, format and `x-orcon-widget`; validation from the same schema; no hand-written form per connector. Custom widgets are registered in one registry and need a spec.
