# Expression runtime module

`quickjs.wasm` is the WebAssembly module the expression sandbox runs (ADR-0018 section 3): QuickJS-ng compiled to a WASI reactor, plus `orcon_qjs.c`, a small C shim written for Orcon that exposes `orcon_init`, `orcon_load`, `orcon_bind`, `orcon_eval`, `orcon_out_ptr`, `orcon_out_len`, `orcon_memory_used`, `orcon_alloc` and `orcon_free`, and imports `orcon_v1.host_call` and `orcon_v1.interrupt`. The module uses no std/os/module-loader code of QuickJS and no filesystem, network or clock.

The binary is committed, as the reviewed output of `build.sh`; CI does not rebuild it. Rebuilding with the same toolchain archive gives the same bytes (SHA-256 of `quickjs.wasm`: `4b50119b629fa3d6682b85f39cd5f669eda221f411db9bc13a495b358481084e`, checked with the arm64-macos archive).

## Rebuilding

```sh
sh internal/adapter/wazero/assets/build.sh
```

The script downloads wasi-sdk 34.0, QuickJS-ng 0.17.0 and nothing else, checks each download against the SHA-256 digest written in the script, applies `quickjs-interrupt-poll.patch` to `quickjs.c`, compiles `orcon_qjs.c` with the QuickJS sources (`quickjs.c`, `libregexp.c`, `libunicode.c`, `dtoa.c`; not `quickjs-libc.c`) and writes `quickjs.wasm` and `LICENSE.quickjs`. Set `WASI_SDK_PLATFORM` and `WASI_SDK_SHA256` to use the toolchain archive of another build machine; the module itself does not depend on the machine.

## Files

- `quickjs.wasm`: the module (MIT, QuickJS-ng; `LICENSE.quickjs` is its licence text).
- `quickjs-interrupt-poll.patch`: the Orcon change to QuickJS-ng 0.17.0 (a unified diff of `quickjs.c`, `libunicode.c`, `libunicode.h` and `libregexp.c`; SPEC-001 amendment 10, sections A.4 and C). The patched module is "QuickJS-ng 0.17.0 + interrupt-poll patch, MIT"; the patch is versioned with the module and rebuilt with it. It does two things, with two helpers placed right after `struct JSContext`:
  - `js_poll_work(ctx, units)` subtracts the work done from the interrupt counter and calls the interrupt handler when the counter reaches zero. It sits inside the loops of every native function whose single call on the largest input that fits the 64 MiB memory cap can exceed 20 ms: the search, replace, split, repeat, pad, trim, case, URI and base64 and hex functions of strings; JSON; the array methods (`indexOf`, `includes`, `fill`, `reverse`, `slice`, `splice`, `sort`, `concat`, `flat`, `join`, `with`, `from` and the rest), the typed array methods, the iterator helpers, property enumeration (`Object.keys`, `assign`, `freeze`, `getOwnPropertyDescriptors`, `for...in`, spread), the multi-precision loops of BigInt (multiplication, division, to and from string), the tokenizer, the regular expression compiler, and the comparators of `sort`. Helpers that have no context (the encoders, the multi-precision routines, the Unicode normalizer) poll through `orcon_poll`, which uses the context of the runtime; the normalizer and the regular expression compiler call hooks set by the embedder.
  - `js_charge_work(ctx, units)` never throws and never calls the handler: it subtracts from the counter, adds to a second counter of work since the last return to the host, and, past `ORCON_YIELD_UNITS` (20000), gives the host a safe point (see "Yield point"). It can sit anywhere, the allocator included. When the counter reaches zero the next poll that already exists (a backward jump or a call in the interpreter, or a `js_poll_work`) calls the handler. This is what stops an interpreted loop that calls an expensive native function: the counter drains by the work done, not by the number of bytecode operations. One unit is about the cost of an average bytecode operation (10 to 20 ns). The interrupt counter starts at 5000 (`JS_INTERRUPT_COUNTER_INIT`), so a pure bytecode loop reaches the host in well under a millisecond. The charges are: allocation, `size >> 6` (64 bytes per unit); bulk copies and fills of array buffers and typed arrays and the move of `shift`, `size >> 6`; string comparison and equality, `length >> 2`; the reversal of a typed array, `length >> 2`; hashing a string key longer than 64 Ki characters, `length >> 3`; the search of `indexOf` and `includes`, 16 plus the needle length divided by 8 per step. Any native whose work scales with the size of its input is charged, even when one call of it is short, because a loop of calls multiplies the work. The test judges the result (the bounds of ADR-0018 section 3), not the scale.
  - Yield point (SPEC-001 amendment 10, D-3.4). Go cannot stop the world, run a timer or collect garbage while a compiled function runs without calling the host, so a long native stretch delays the whole process. `orcon_yield` (called by `js_charge_work`, by `orcon_yield_global` in code that has no context, and by the `ORCON_TICK()` that the patch puts in the loops of functions without a context) calls the host import `orcon_v1.interrupt` only to give Go a safe point; the answer is stored in a flag (`orcon_stop`) that the next poll able to stop consumes, so the guest stops at the next safe place and not in the middle of a C function. Removing the handler (`JS_SetInterruptHandler(rt, NULL, NULL)`, done by `orcon_eval` before it formats the exception) clears the flag. The target is at most 1 ms between two host calls; `TestSandboxIsolationStretch` holds the interpreted loops and the cases of the abandon table to 2 ms and the covered natives (one large copy or fill) to 5 ms, and `TestAbandonUnderLoad` and `FuzzSandboxAbandon` hold the lateness of a 1 ms timer, and the garbage-collection pauses, to 15 ms with no retry (owner ruling of 2026-10-13, which accepts up to 20 ms). These bounds hold until BL-033 moves the sandbox to a separate process, a gate before the first release.
  - Chunk sizes. Primitives that copy, fill, search or hash a large block do it in chunks with a yield point between them: 256 KiB for byte-wide operations (`memchr`, `memcmp`, `memcpy`, `memset` of big blocks, the growth of a block by `realloc`, the zeroing of a big `calloc`) and 16384 elements for element-wide loops (array `shift`, the character loops of string conversion and comparison, hashing, single-character search).
- `native-loops.txt`: generated by `build.sh` with `tools/qjsloops`; it lists every C function of the patched `quickjs.c` that has a loop bounded by the input or a memory move of variable length, and whether it polls or charges the counter. Changing the patch or the QuickJS-ng version changes the file and must be reviewed in the same pull request; `make check` does not regenerate it (it downloads nothing).
- `orcon_qjs.c`: the shim (Apache-2.0, The Orcon Authors).
- `build.sh`: the build.
