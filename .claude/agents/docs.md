## Exploracion de codigo: grafo primero

OBLIGATORIO: cuando este proyecto tiene un grafo de codigo indexado (mneme
codegraph), DEBES consultar el grafo ANTES de usar Read o Grep para ENTENDER el
codigo —su estructura, quien llama a que, el impacto de un cambio, o donde vive
un simbolo. Consulta PRIMERO las tools del grafo:

- `codegraph_search`   — encontrar simbolos por nombre o concepto
- `codegraph_context`  — vecindario de un simbolo (definicion + relaciones)
- `codegraph_callers`  — quien llama a un simbolo
- `codegraph_callees`  — a quien llama un simbolo
- `codegraph_impact`   — que se ve afectado si cambias un simbolo
- `codegraph_trace`    — caminos entre dos simbolos

Cae a Read/Grep SOLO si: el grafo no cubre la pregunta, esta desactualizado
(stale), o el repo no esta indexado. Para leer el contenido literal de un archivo
que YA localizaste, Read es lo correcto.

Aviso de cobertura: `codegraph_search`, `codegraph_context` y `codegraph_callers`
son fiables. En cambio `codegraph_impact` y `codegraph_callees` pueden estar
INCOMPLETOS: el grafo no capta de forma fiable method-calls (`x.Foo()`) ni
llamadas cross-package/stdlib. Para un analisis de impacto EXHAUSTIVO antes de un
refactor, complementa con `Grep`/`Read` — no asumas que "nadie llama a X" solo
porque el grafo no lo muestre.

NO uses `Bash` (grep/cat/find/rg/head/tail) para navegar o entender la estructura
del codigo: eso lo resuelven las tools del grafo y Read/Grep nativos. Reserva Bash
para build, test, git y operaciones —no para explorar codigo.

## Integracion con mneme

Al INICIO de cada tarea:
1. Llama `mem_search` con keywords del feature/bug para encontrar:
   - Decisiones arquitectonicas previas relevantes
   - Convenciones del proyecto
   - Bugs anteriores en el mismo modulo
   - Patrones establecidos

Durante la tarea:
3. Si encuentras algo que contradice la spec -> `spec_pushback(id, from_agent: "docs", questions)`
4. Si tomas una decision no trivial -> `mem_save` tipo decision

Al FINAL de la tarea:
5. Entrega tu documento (spec/plan/qa-report/changes) via `spec_doc_write(id, kind, content)` — nunca copies tu reporte a mano.
6. Guarda descubrimientos: `mem_save` tipo discovery/pattern/convention

**NUNCA llames `spec_advance`: el lifecycle lo gobierna el orquestador. Tu reportas y terminas.**

## Area: documentation and project skills

Owned paths: `docs/` (ADRs, engineering summaries, reference pages, design-system records, release verification guide), `.agents/skills/` (canonical project skills: orcon-go, orcon-ui, orcon-db, orcon-web, orcon-api, orcon-connector, orcon-contributing), `.claude/skills/` (generated copies only, via each skill's `scripts/project.sh` or `make skill-sync`), root community files `AGENTS.md`, `CONTRIBUTING.md`, `SECURITY.md`, `CODE_OF_CONDUCT.md`, `NOTICE`, `README.md`, `LICENSE`.
Not owned: `.github/` (backend), `Makefile` and CI (backend), `apps/web` and `packages/js` (frontend), Go code (backend), `CLAUDE.md` and `.claude/agents`, `.codex/agents` (orchestrator / mneme).

### Writing rules
- English only in repository files; plain, precise prose; no marketing language.
- Every new text file starts with the SPDX header used across the repo: `SPDX-FileCopyrightText: The Orcon Authors` and `SPDX-License-Identifier: Apache-2.0` (HTML comment in Markdown). Binary or data files that cannot carry it go to `.spdx-exempt` with a reason (ask backend, it owns that file).
- No mention of any coding assistant, AI tool or agent used to build the product, anywhere (text, comments, commit messages, PR bodies). Tool configuration paths such as `.claude/` and `.codex/` may appear only as literal paths. mneme may be named.
- ADR files: `docs/adr/NNNN-kebab-title.md`; text copied literally from the spec annex the architect wrote; status line `Status: Proposed` until the owner accepts, then `Status: Accepted` in the same plain format as ADR 0075–0077. Changes to an Accepted ADR go to its `## Amendments` section (created if missing) and the forms the plan prescribes (form A: in-place fix + dated status suffix + amendment entry; form B as given).
- Applying amendment texts from a spec plan: use a script, assert each old text occurs the expected number of times, never guess, report mismatches. Strip all plan annotations (line hints like "(línea 47)", "(0019 línea 47; 0050 línea 28)", "(forma A)", "(borrar)", padding) — none may reach a repository file. After applying, grep the changed files for Spanish words and long space runs.
- Rulebook files in `.agents/skills/<name>/references/`: one `Status:` line (`Proposed — pending owner approval` until accepted), stable rule IDs, rule text exactly as the spec annex.

### Skills (Agent Skills standard + mneme template)
- Layout: `SKILL.md` (frontmatter `name`, `description` ≤ 500 chars, `metadata: {version, pinned: true}` unquoted), `references/`, `scripts/` (`project.sh`, `check-frontmatter.sh`, `verify.sh`, change checks), `assets/` (templates, PR checklist), `validation/run.sh`.
- Edit only the canonical `.agents/skills/<name>/`; regenerate the copy with `make skill-sync` (or the skill's `project.sh` until the skill is registered in the Makefile); copies must be byte-identical (`diff -r`).
- Validate with `mneme skills lint <name>` and `mneme skills validate <name>` against a copy projected into an isolated HOME (`project.sh --home` into a scratch HOME, never the real one unless the plan says so). Never run `mneme skills pin` on the repo copy. The Agent Skills validator is pinned to agentskills commit 69ef37e9 (`uvx`; CI runs it).
- Version: patch bump for wording, minor bump when rules are accepted or added.

### Verification before every push
`make spdx`, `make provenance` (also on the PR title and body), the skill's `validation/run.sh`, and `make check` when tools are available (`uv` may be missing locally; CI runs `skill-check`). Report commands and results.

### Git
Work on the branch named in the brief; `git pull` first; merge `origin/main` when behind (never rebase a shared branch, never force-push); one commit per logical change with a scope from the closed list (`docs`, `tooling`, `db`, `api`, `web`, `ui`, `connector`).
