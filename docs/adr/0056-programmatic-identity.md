# ADR-0056 — Programmatic identity: API key principal, service accounts, scoped keys, OAuth2 client credentials and federated workload identity

Status: **Accepted** | Date: 2026-10-11 (amended 2026-10-12: owner answers Q1–Q14, human-attention surface; ADR-0080 enum form; ADR-0077 schema rules and engine lookups) (amended 2026-10-13: stored enumerated values are UPPER_SNAKE, ADR-0015 §2; audit request channel split into `channel` and `sdkLanguage`)

Accepted by the owner on 2026-10-12 via SPEC-005.

## Context
P2: service accounts (non-human principals owned by an organization, surviving employee offboarding); API keys with permissions selected from the permission catalog (least privilege); mandatory expiry (default 90 days, configurable) with overlap rotation; OAuth2 client credentials for short-lived machine tokens; every use audited; instant revocation; personal keys ≤ the person's permissions. ADR-0038 §3 reserves the `apiKey` principal "always bound to a user or service account and limited to a subset of its permissions" and §6 the authenticator chain slot; ADR-0041 defines the catalog (including `service-account:manage` and `apikey:manage-org`), evaluation and epoch-based revocation; ADR-0048 the audit log. Owner decisions of 2026-10-12: every read audited (Q5), federated workload identity for CI in V1 (Q7), expiry limits (Q12), personal-key policy (Q13) and predefined role grants (Q14).

## Decision

### 1. Service accounts
Service accounts are the `serviceAccount` principal of ADR-0038 §3: `service_account(org_id, id, principal_id, name, description, status: ACTIVE|DISABLED, created_by_principal_id?, created_at, revision)`, with a unique `principal_id` referencing the instance table `principal` (`ON DELETE CASCADE`, ADR-0077 §8), bound to roles through `role_binding` (ADR-0041 §1) at organization or project scope, including custom roles. They never sign in interactively and never approve confirmations (ADR-0059 §5). Managed with `service-account:manage`. Disabling one increments the organization's `authorization_epoch` and invalidates all its keys and tokens.

### 2. API key principal and effective permissions
- Authenticating a key or token yields `Principal{kind: apiKey, id: <key id>, boundTo: {kind: user|serviceAccount, id}, credentialType: sak|pak|oat, scopes, projectIds?}` with `AuthContext.OrgID` fixed to the key's organization. In API representations these values are UPPER_SNAKE (`kind: SERVICE_ACCOUNT`, `credentialType: SAK|PAK|OAT`; ADR-0080 §3). Actor columns written on behalf of a key record the bound principal; the audit record keeps the key (ADR-0038 §3).
- The struct shows Go values; stored and API values are `SAK`, `PAK` and `OAT` (see below).
- Effective permission check: `Authorize` evaluates the request for `boundTo` (ADR-0041 §6) and additionally requires the permission to be in `scopes` and the project (if any) in `projectIds`. Demoting the person or service account therefore shrinks every key immediately; personal keys never exceed the person.
- Creation rules (no escalation, like ADR-0041 §4): the creator can only include permissions it holds in that scope. Personal keys require `apikey:create-personal`; managing other users' keys requires `apikey:manage-org`; service-account keys require `service-account:manage`.
- Predefined role grants of the catalog v2 permissions (owner decision Q14): `apikey:create-personal` and `mcp:use` → Owner, Admin, Member (a Member can only create keys with a subset of the Member's own permissions); `event-subscription:manage` → Owner, Admin; `git:manage` → Project Admin; `git:sync` → Project Admin, Editor.
- Personal keys (owner decision Q13): allowed by default for holders of `apikey:create-personal`. Organization policy (ADR-0038 §8) can forbid them; enabling that switch revokes all existing personal keys of the organization immediately (audited `apikey.personal_keys_forbidden` with the count) and further creation returns `403 personal-keys-disabled`.
- Organization policy (ADR-0038 §8): forbid personal keys, maximum lifetimes (general and personal), require `projectIds` for service-account keys.
- Instance-scope operations (ADR-0038 §4) are not available to `apiKey` principals in v1; they require an interactive session of an instance administrator.

### 3. Token format
`orcon_<type>_<id>_<secret>_<check>`: `type` ∈ `sak` (service-account key), `pak` (personal key), `ocs` (OAuth client secret), `oat` (OAuth access token); `id` 16 chars Crockford base32 (lookup key); `secret` 43 chars base62 = 256 random bits from the OS CSPRNG; `check` 6 chars base62 of CRC32 over the preceding characters. Published regex: `orcon_(sak|pak|ocs|oat)_[0-9A-HJKMNP-TV-Z]{16}_[0-9A-Za-z]{43}_[0-9A-Za-z]{6}` in `docs/reference/token-formats.md`, for secret scanners and partner programs (best-effort; third parties cannot reach self-hosted instances, so revocation stays with the instance owner). The lowercase prefixes are part of the token format and do not change with the API enum form. Webhook secrets use `whsec_` (ADR-0055 §5).

### 4. Storage and verification
`api_key(org_id, id, bound_principal_id, name, token_type: SAK|PAK, token_hash, token_suffix, expires_at, created_by_principal_id?, created_at, last_used_at, revoked_at, revoked_by_principal_id?, rotated_from_api_key_id?, overlap_until_at?, revision)`; `bound_principal_id` references `principal` (`ON DELETE CASCADE`: a key never outlives its principal); scopes and project restrictions are child tables `api_key_scope(org_id, id, api_key_id, permission)` and `api_key_project(org_id, id, api_key_id, project_id)`. Only `SHA-256(full token)`, `id` and the last 4 characters (`token_suffix`) are stored (a slow hash is unnecessary for 256-bit secrets). `apiKeyAuthenticator` is added to the ADR-0038 §6 chain after the session cookie: parse, verify checksum (reject without DB access), look up by `id`, constant-time compare, check status, expiry, overlap and the bound principal's status, then build the principal. Results are cached per process under the organization's `authorization_epoch` (ADR-0041 §7). Key tables are organization tables (RLS, ADR-0046); lookup by `id` before the organization is known uses the engine function `orcon_engine.resolve_api_key(key_id)`, which returns `(org_id, token_hash, status)` only (ADR-0047 §2).

### 5. Expiry and rotation
- `expires_at` mandatory (owner decision Q12): default 90 days; organization maximum (default 365 days, never above the instance limit); no non-expiring keys, including service-account keys and OAuth client secrets. Personal keys have their own maximum, default 30 days (organization-configurable, never above the general maximum), which is also their default lifetime (Q13). Pre-expiry warnings: events `api_key.expiring` at 14 and 3 days and an editor notice to the key's owner.
- `POST /api-keys/{apiKeyId}/rotate` creates a successor with identical scopes and bound principal; the predecessor stays valid until `overlap_until_at` (default 7 days, max 30) and use during overlap is audited; either can be revoked early.

### 6. Revocation
Revoking a key, disabling a service account, removing or suspending a membership, SCIM/LDAP deprovisioning (SPEC-004 R-AUTH-08), losing `apikey:create-personal` (for that person's personal keys) or enabling the organization switch that forbids personal keys (owner decision Q13) sets `revoked_at` where applicable; losing any other permission needs no revocation because the intersection of §2 shrinks the key at the next request. Every one of these changes (and every permission change) increments `authorization_epoch` with `pg_notify('orcon_authz')` in the same transaction; effective cluster-wide within 1 s (ADR-0041 §7), verified by a multi-process test. Open SSE streams and MCP sessions of the key are closed.

### 7. OAuth2 client credentials
- `oauth_client(org_id, id, service_account_id, name, client_identifier, secret_hash?, json_web_key_set_document?, json_web_key_set_document_format?, authentication_method: client_secret_basic|client_secret_post|private_key_jwt, token_lifetime_seconds, expires_at, revoked_at, revoked_by_principal_id?, revision)`, with child tables `oauth_client_scope` and `oauth_client_project`, managed with `service-account:manage`. The authentication method values come from the OAuth standards and keep their form in the API (`x-orcon-enum-kind: identifier`). Client secrets use the `ocs` format and the expiry/rotation rules of keys; `private_key_jwt` (RFC 7523) lets CI use asymmetric keys.
- `POST /api/v1/oauth/token` (`grant_type=client_credentials`, optional `scope` ⊆ client scopes) returns an opaque `oat` token, TTL default 15 min, max 1 h, stored hashed in `oauth_token(org_id, id, oauth_client_id?, workload_identity_trust_id?, token_hash, expires_at, revoked_at)` with a check that exactly one of the two origins is set and a child table `oauth_token_scope`; no refresh tokens. The token authenticates as an `apiKey` principal bound to the service account; its lookup before the organization is known is `orcon_engine.resolve_oauth_token(token_hash)` (ADR-0047 §2).
- `POST /api/v1/oauth/revoke` (RFC 7009), `POST /api/v1/oauth/introspect` (RFC 7662), metadata at `/.well-known/oauth-authorization-server` (RFC 8414). These endpoints are tagged `protocol` and sit outside the path grammar of ADR-0080.
- Federated workload identity for CI: §9 (owner decision Q7).

### 8. Audit
- Every request authenticated by a key or token, reads and denials included (owner decision Q5), produces `api.request` (`orcon/audit@1`, ADR-0048 §1) with actor `{kind: API_KEY, id, boundTo}`, `details{operationId, channel, sdkLanguage?, mcpClient?, credentialType}`, target, outcome and request metadata. `channel` is `API`, `CLI`, `SDK` or `MCP`; `sdkLanguage` is present only when `channel` is `SDK` and holds the lowercase identifier of the language of the generated SDK (`typescript`, `go`, `python`), an identifier that keeps its form; `credentialType` is `SAK`, `PAK` or `OAT`. `MCP` is set by the in-process dispatch of ADR-0059 §3; `CLI` and `SDK` come from the product token the generated CLI and SDKs send in `User-Agent` (`orcon-cli/<version>`, `orcon-sdk-<language>/<version>`); any other request, including a product token naming a language without a generated SDK, is `API`. Except for `MCP` the channel is declared by the client: it explains a request and never authorizes one. Mutations insert it in the action's transaction (ADR-0048 §2); reads go through a per-process batcher into `audit_pending` (≤ 50 ms or 1,000 events). Denied requests are audited.
- Lifecycle events: `apikey.created|rotated|revoked|expired|used_during_overlap`, `apikey.personal_keys_forbidden`, `oauth_client.created|rotated|revoked`, `oauth.token_issued|token_revoked` (with issuer and federated subject for §9 exchanges), `workload_identity.created|updated|deleted`, `service_account.created|deleted|token_rotated` (existing).
- `last_used_at` updated at most once per minute per key.

### 9. Federated workload identity for CI (owner decision Q7)
- Purpose: CI systems (GitHub Actions, GitLab CI, Kubernetes service accounts) exchange the OIDC token their platform issues for a short-lived Orcon token, so no Orcon secret is stored in CI.
- `workload_identity_trust(org_id, id, service_account_id, name, issuer, audience, claim_condition_document, claim_condition_document_format, token_lifetime_seconds, status, created_by_principal_id?, created_at, revision)`, with child tables `workload_identity_trust_scope` and `workload_identity_trust_project`, managed with `service-account:manage`; scopes follow the creation rules of §2. The claim conditions are a document read whole at exchange time: exact-match or anchored glob rules on token claims (e.g. `sub = repo:acme/flows:ref:refs/heads/main`, `repository`, `ref`, `environment`, Kubernetes `sub = system:serviceaccount:<ns>:<name>`); at least one condition on a claim that identifies the workload is mandatory (a trust that only checks the issuer cannot be created). Presets for GitHub Actions, GitLab CI and Kubernetes are documented.
- Exchange: `POST /api/v1/oauth/token` with `grant_type=urn:ietf:params:oauth:grant-type:token-exchange` (RFC 8693), `subject_token_type=urn:ietf:params:oauth:token-type:jwt`, optional `scope` ⊆ trust scopes. Validation: issuer discovery and JWKS fetched through the egress client (ADR-0029 §8) and cached with bounded lifetime; signature; exact `iss`; `aud` equals the trust audience; `exp`/`nbf`/`iat` with 60 s clock skew; token age ≤ 10 minutes; every claim condition matches; the trust and its service account are active. Failure → `400 federated-token-rejected` with a generic message (details only in the audit record). Success → `oat` token (§7, `workload_identity_trust_id` set) bound to the service account, TTL ≤ the trust's token lifetime (max 1 h).
- Audit: `oauth.token_issued` with issuer, federated subject and trust id; rejected exchanges are audited with the reason.
- Delivered as slice API3b after API3.

## Consequences
Automation survives staff changes; leaked keys are recognizable and short-lived; least privilege is enforced by intersection inside the existing evaluator; revocation shares the bounded mechanism of user permissions.

## Alternatives considered
JWT access tokens (revocation needs a lookup anyway; contents readable); slow password hashes for 256-bit secrets (cost without benefit); static permission snapshots in keys (demotions would not apply); non-expiring keys (rejected by P2); a polymorphic `(bound_kind, bound_id)` pair (rejected by ADR-0077: the `principal` table gives one foreign key for users and service accounts).

## Amendments
Changes applied after acceptance; each entry names its source.

- **SPEC-009 K19 (2026-10-13, owner decision).** §1 and §4 (`service_account.status`, `api_key.token_type`; the prefix inside a token keeps its lowercase form): enumerated columns store the same UPPER_SNAKE values the API exposes (ADR-0015 §2 applies to every table); no adapter translates an enumerated value between the database and the API.
- **Owner decision on the audit request channel (2026-10-13, SPEC-004 and SPEC-005).** §8 (`api.request` details; actor kind `API_KEY` and credential type `SAK|PAK|OAT` as ADR-0048 §1 spells them): the request channel is `API`, `CLI`, `SDK` or `MCP`, and the SDK language is a separate lowercase identifier, `sdkLanguage`, present only when the channel is `SDK`. This replaces the form `api|cli|sdk-<lang>|mcp`, whose variable part could not follow the UPPER_SNAKE rule for public values.
