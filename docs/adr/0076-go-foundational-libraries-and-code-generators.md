# ADR 0076: Go foundational libraries and code generators

Status: Proposed

## Context
Foundational dependencies need an accepted ADR (implementation contract, docs/engineering/implementation-contract.md). Earlier designs proposed pgx/v5 and modernc.org/sqlite and left the Go OpenAPI generator to measurement. The maintainers decided the remaining choices.

## Decision
1. HTTP server: standard library net/http with Go 1.22+ ServeMux patterns. Fiber and fasthttp are rejected (not net/http compatible; they break standard middleware and OpenTelemetry instrumentation).
2. API: OpenAPI 3.1 is the source of truth; Go server types and strict handler interfaces are generated by oapi-codegen v2 (Apache-2.0) with std-http-server and strict-server; generated code is committed and checked fresh in CI. Supersedes the "chosen by measurement" clause of ADR-0054 §1.
3. SQL: hand-written SQL compiled to Go by sqlc (MIT) with separate SQLite (modernc.org/sqlite, BSD-3, database/sql) and PostgreSQL (pgx/v5, MIT, native) query sets; no ORM, no query builder. Generated code is committed and checked fresh.
4. Logging: log/slog. Metrics and traces: OpenTelemetry Go (Apache-2.0); only its API packages are used outside the telemetry adapter.
5. Tests: standard testing package, go-cmp (BSD-3), goleak (MIT), testcontainers-go (MIT) for PostgreSQL. No testify, no generated mocks.

## Consequences
No framework lock-in; every net/http middleware and instrumentation library applies; schema and query errors surface at generation time.

## Alternatives considered
ogen (rejected by maintainer decision); Fiber, Echo, Gin (Fiber incompatible; the others add little over ServeMux); GORM, ent, bun, sqlx (hide SQL, weaker dialect features such as FTS5 and row-level security); zap, zerolog (slog is standard).
