# ADR-0015 — Storage contract: logical schema, SQLite and PostgreSQL adapters, migrations

Status: **Accepted** | Date: 2026-10-11 | Amended: 2026-10-12 (ADR-0077); 2026-10-13 (SPEC-009: unique execution event order; stored enumerated values are UPPER_SNAKE in every table)

Accepted by the owner on 2026-10-12 via SPEC-001.

## Context
ADR-0004 (SQLite local, PostgreSQL distributed, same semantics) and D19 (SQLite for single-server production, same conformance suite on both, automatic migrations, official SQLite→PostgreSQL migration, older binary refuses a newer schema). ADR-0077 (database schema standards) amends §2 and §3 and adds the organization column, the instance tables, the principal table, the engine-plane lookups and the PostgreSQL 14 limits; this text already includes those amendments. The database rulebook (`.agents/skills/orcon-db/references/`) and the accepted Go rulebook (DA-1 to DA-8, DA-3 as amended) govern every detail not stated here.

## Decision

### 1. Store interface
The transactional operations the engine needs (claim, renew, fenced checkpoint, join arrival, timer firing, journal batch, etc.) are ports declared by each consuming area (`internal/execution`, `internal/journal`, …; ADR-0075). Adapters: `internal/adapter/sqlite`, `internal/adapter/postgres`. `internal/adapter/storetest` is the shared conformance suite; the engine conformance suite also runs against both. The real migrations are also checked by `tools/dbcheck` and `internal/adapter/storetest/dbrules` (ADR-0077 §1) on SQLite and PostgreSQL 14 and 17.

### 2. Type mapping (as amended by ADR-0077 §2)
| Logical | PostgreSQL | SQLite (every table STRICT) |
|---|---|---|
| ID | `uuid` | `BLOB` with `CHECK (length(x) = 16)` (RFC 9562 byte order) |
| Timestamp | `timestamptz` (session time zone UTC) | `INTEGER` (unix µs UTC) |
| JSON document | `bytea` by default; `jsonb` only for a column with an approved JSON-path exception | `BLOB` |
| Bytes | `bytea` | `BLOB` |
| Bool | `boolean` | `INTEGER` with `CHECK (x IN (0, 1))` |
| Integer, counter, duration, money | `bigint` | `INTEGER` |
| Sequence number | non-key `sequence_number` `bigint` with a UNIQUE constraint | non-key `sequence_number` `INTEGER` assigned by the single writer, UNIQUE |
- IDs are generated by the application only (UUIDv7, or the deterministic UUIDs of ADR-0008 §6); never by a column default.
- Every JSON document column `<name>_document` has a sibling `<name>_document_format` tag (`orcon/<kind>@<major>`). No query reads inside a JSON document without a written, owner-approved exception (Go rulebook DA-3 as amended; ADR-0077 §9); data that is filtered, sorted, joined or referenced lives in a real column written in the same transaction.
- Not used: PostgreSQL ENUM types, domains, arrays, `varchar(n)`, `timestamp` without time zone, `date`, `time`, `interval`, `money`, floating point and serial types. Enumerated values are text with a CHECK; the stored values are the same UPPER_SNAKE values the API and the flow document use (ADR-0080 §3), one spelling everywhere.

### 3. Logical schema (as amended by ADR-0077 §3; columns abbreviated with "…" are completed by the implementing slice under the database rulebook)
Every table has `id` (primary key), `created_at`, and `updated_at` unless append-only. Organization-scoped tables have `org_id` NOT NULL, composite foreign keys `(org_id, <parent>_id) REFERENCES <parent>(org_id, id)`, and `UNIQUE (org_id, id)` when referenced; foreign keys from organization-scoped tables to instance tables are single-column. JSON columns are `<name>_document` with `<name>_document_format`. Actor columns are `<verb>_by_principal_id`, nullable, with a single-column foreign key to `principal(id)` `ON DELETE SET NULL` and a supporting index; the audit log keeps the actor identity without a foreign key.
- Instance tables: `schema_migration(version PK, checksum, applied_at, binary_version, compatibility_floor)` (sole exception to the `id` rule); `worker(id, role, host, version, started_at, heartbeat_at)` (informational); `org(id, name, status, …)` (isolated by its own id); `principal(id, kind, created_at)` with `kind` in `USER`, `SERVICE_ACCOUNT`, `SYSTEM` (text with a CHECK; the same value the API exposes) and exactly one `SYSTEM` row per installation (`uq_principal_kind` partial unique index `WHERE kind = 'SYSTEM'`); `instance_alert(id, kind, subject_reference, status, level, summary, affected_reference_document, acknowledged_by_principal_id, acknowledged_at, next_escalation_at, closed_at, closed_reason)`.
- `project(org_id, id, name, slug, environment, is_protected)`.
- `flow(org_id, id, project_id, name, draft_document, draft_revision, active_flow_version_id, deleted_at, deleted_by_principal_id)`; name unique per project among non-deleted flows (`uq_flow_org_id_project_id_name … WHERE deleted_at IS NULL`). `flow` is the only table with soft delete (ADR-0007 §10).
- `flow_version(org_id, id, flow_id, version_number, document, content_hash, warning_document, published_by_principal_id, published_at)` append-only; unique `(org_id, flow_id, version_number)`.
- `flow_snapshot(org_id, id, flow_id, content_hash, document)` append-only; unique `(org_id, content_hash)`.
- `call_edge(org_id, id, flow_version_id, target_flow_id, kind, is_intentional, maximum_depth)` append-only.
- `execution(org_id, id, project_id, flow_id, flow_version_id, flow_snapshot_id, status, mode, priority, parent_execution_id, parent_token_id, root_execution_id, call_depth, call_chain_document, retried_execution_id, run_generation, cancel_requested_at, undo_requested_at, runnable_count, leased_count, waiting_count, suspended_count, active_milliseconds, throttle_kind, error_document, summary_document, data_key_wrapped, started_at, finished_at)`; exactly one of `flow_version_id`, `flow_snapshot_id` (`ck_execution_revision`).

- `node_execution(org_id, id, execution_id, token_id, node_id, scope_path, status, attempt_count, item_state_document, item_route_document, output_reference_document, error_document, started_at, finished_at)`.
- `task_attempt(org_id, id, execution_id, node_execution_id, attempt_number, lease_epoch, worker_id, status, item_document, error_document, started_at, finished_at)`; `worker_id` references the instance table `worker` `ON DELETE SET NULL`.
- `node_output(org_id, id, execution_id, node_execution_id, port, item_count, encoding, inline_document, blob_id)`.
- `external_operation(org_id, id, execution_id, node_execution_id, item_index, correlation_key, contract_reference, state, batch_key, request_reference, response_reference, dispatch_deadline_at, first_dispatched_at, retry_epoch, compensation_state, resolved_by_principal_id, evidence_reference)`; unique `(org_id, correlation_key)`.
- `join_instance(org_id, id, execution_id, node_id, scope_path, edge_state_document, status, continuation_token_id)`; `join_arrival(org_id, id, execution_id, node_id, scope_path, edge_index, token_id, payload_reference, is_live, arrived_at)`; `merge_tracker(org_id, id, …)`; `multi_instance(org_id, id, execution_id, node_id, scope_path, total, started, completed, in_flight, status)`.

Tables of other designs (triggers, connectors, identity, AI) follow the same rules (ADR-0077 §5).

### 4. Migrations
- Embedded per-dialect migration files with identical numbering (`internal/adapter/sqlite/migrations/NNNN_<name>.sql` and `internal/adapter/postgres/migrations/NNNN_<name>.sql`, both mandatory); applied automatically at startup under a migration lock (PostgreSQL advisory lock; SQLite exclusive transaction); version, checksum, binary version and compatibility floor recorded in `schema_migration`.
- Each file carries a header (`-- orcon:kind additive|expand|contract|rebuild|data`, `-- orcon:compatibility-floor <version>|self`, `-- orcon:contracts NNNN` for contract migrations, `-- orcon:no-transaction` for a single PostgreSQL `CREATE INDEX CONCURRENTLY`); the checksum is the SHA-256 of the LF-normalized file, the same value listed in the dialect's `migrations.sum` (ADR-0077 §10). A merged migration is immutable.
- **Compatibility floor.** Every migration declares its compatibility floor: the oldest Orcon binary version that runs correctly against the schema after that migration. If a migration declares none (`self`), its floor is its own release. The schema's effective floor is the maximum `compatibility_floor` over applied migrations.
- A binary refuses to start only if its version is lower than the effective floor. The error names the binary version, the schema version and the minimum binary version required ("upgrade to ≥ X"). A binary older than the schema but at or above the floor runs (rolling upgrade). This keeps D19 literally for breaking migrations (floor = their own release) and relaxes it only where a migration declares compatibility.
- Additive migrations (new tables, new nullable columns, new indexes, new values that older readers tolerate) set the floor to an older release, normally the previous minor release.
- **Expand/contract.** A breaking schema change is split across two releases: release N expands (adds the new structure and writes both forms; floor N−1), release N+1 contracts (removes the old structure; floor N). Dropping or renaming a column or table in a single release is rejected by a migration lint in CI.
- **Floor verification.** For every migration with a declared floor F, CI starts the binary of release F against a database migrated by the current binary and runs the `storetest` smoke subset; failure blocks the merge. A test also checks that a binary below the floor refuses with the error above.
- **Upgrade verification.** Each migration ships seed and verify files per dialect; CI applies migrations 1..N−1 with their seeds, applies N and runs the verify file and the integrity checks on SQLite and PostgreSQL 14 and 17 (ADR-0077 §1).
- Checksum mismatch of an applied migration → refuse to start.

### 5. SQLite adapter
One process per database file (exclusive lock file); WAL; `synchronous=FULL` default (durable on power loss; `NORMAL` documented as a weaker opt-in); `foreign_keys=ON` on every connection; a single writer goroutine applying transactions with group commit; a read connection pool; `busy_timeout`. Driver: `modernc.org/sqlite` (BSD-3, pure Go, keeps cross-compilation of the single binary). Measurement plan: the D20 scenarios S1/S2/S4 run on SQLite; if the gate fails due to the driver, `ncruces/go-sqlite3` (MIT, WASM) and `mattn/go-sqlite3` (MIT, CGO) are benchmarked; switching requires an ADR amendment.

### 6. PostgreSQL adapter
`pgx/v5` (MIT); READ COMMITTED; `FOR UPDATE SKIP LOCKED`; LISTEN/NOTIFY on a dedicated connection; advisory locks for migrations and singleton jobs (reaper, pruning); session time zone UTC. Supported versions declared in docs (≥ 14); DDL uses only features available in PostgreSQL 14 (no `NULLS NOT DISTINCT`, no `security_invoker` views, no `MERGE`, no `ON DELETE SET NULL (column)`). The event table's primary key is `id`; its unique constraint `(org_id, execution_id, sequence_number)` serves ordered reads. Partitioning the table by time later needs the partition column in the primary key and in that constraint, and is decided by its own ADR.

### 7. SQLite → PostgreSQL migration
`orcon store migrate-to-postgres --from <sqlite path> --to <dsn>`: requires the source to be stopped (lock file), copies all tables in dependency order preserving ids, copies filesystem blobs into the target blob backend, resets leases, verifies per-table row counts and content checksums, and refuses a non-empty target.

### 8. Isolation and engine-plane functions (ADR-0046/0047 as amended by ADR-0077 §6)
- No views on organization data: PostgreSQL 14 views run with their owner's privileges and bypass row-level security. The first PostgreSQL migration revokes `CREATE` on schema `public` from `PUBLIC`.
- Work that crosses organizations (claim, renew, reaper, timer firing, outbox delivery, pruning and flow purge) runs in `orcon_engine` functions; every returned row carries `org_id`.
- Lookups that run before the organization is known are engine-plane functions returning `org_id`: in this design `orcon_engine.resolve_wait_secret` (wait resume URLs, ADR-0010 §8); other designs use `resolve_trigger_address`, `resolve_api_key`, `resolve_oauth_token` and `resolve_public_entry`.
- SQLite has no row-level security; the single scoped data-access layer, the static scope check and the adversarial isolation battery apply on both stores (SPEC-004).

## Consequences
One semantics, two adapters, one conformance suite; capacity differences documented (SQLite = one server). Every row carries its organization; constraints catch invalid writes on both stores; schema changes are checked mechanically before merge; an enumerated value has one spelling in the database, the API and the documents.

## Alternatives considered
ORM-level abstraction (rejected: hides locking semantics); SQLite as a shared multi-process coordinator (rejected by ADR-0004); natural primary keys on high-volume tables (rejected by ADR-0077: contradicts the `id` rule and complicates composite foreign keys); querying inside JSON with SQLite JSON1 functions or PostgreSQL `jsonb` (rejected by ADR-0077 and DA-3 as amended); lowercase stored values mapped to UPPER_SNAKE in the API (rejected: two spellings of one value invite mapping bugs).
