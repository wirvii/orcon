# ADR-0055 — Public events: real-time streaming (SSE) and signed outbound webhooks

Status: **Accepted** | Date: 2026-10-11 (amended 2026-10-12: owner answers Q1–Q18, human-attention surface, cross-spec consistency; ADR-0080 enum and `webhooks` rules; ADR-0077 schema rules) (amended 2026-10-13: stored enumerated values are UPPER_SNAKE, ADR-0015 §2)

Accepted by the owner on 2026-10-12 via SPEC-005.

## Context
P1 requires real-time event subscription (e.g. execution finished/failed). The owner requires outbound webhooks signed and retried with the same rigor as inbound ones (SPEC-002). ADR-0009 defines internal events; ADR-0013 §8 the outbox; ADR-0046/0047 organization isolation; ADR-0049 execution-data visibility.

## Decision

### 1. Public event log
- `public_event(org_id, id, sequence_number, project_id, flow_id?, execution_id?, type, subject, occurred_at, data_document, data_document_format, data_schema)`; `sequence_number` is a per-organization monotonic sequence (unique with `org_id`, not a key); inserted **in the same transaction** as the state change it describes. `type`, `project_id` and `flow_id` are real columns so streams and subscriptions filter without reading inside the JSON document.
- Representation: CloudEvents 1.0 JSON structured mode: `specversion`, `id`, `source` (`/orgs/{org}/projects/{project}`), `type` (`dev.orcon.<area>.<event>.v1`), `subject`, `time`, `datacontenttype`, `dataschema`, `data`, extension `orconseq` (the CloudEvents attribute names are fixed by that standard).
- Retention default 7 days (configurable), pruned by the scheduler through an `orcon_engine` function (ADR-0047 §2).

### 2. Public catalog (v1)
`execution.started`, `execution.succeeded`, `execution.failed`, `execution.canceled`, `execution.suspended`, `execution.waiting`, `execution.timeout`, `external_operation.uncertain`, `external_operation.resolved`, `human_task.created`, `execution.awaiting_human`, `execution.awaiting_human.escalated`, `execution.human_resolved`, `flow.published`, `flow.activated`, `flow.deactivated`, `flow.rolled_back`, `flow.deleted`, `trigger.health_changed`, `api_key.expiring`, `api_key.revoked`, `git.sync.succeeded`, `git.sync.failed`, `git.conflict`, `confirmation.requested`, `confirmation.decided`, `operation.finished`, `webhook.subscription_disabled`, `webhook.delivery_dead`, `api.deprecation_notice`, `connector.revoked`. Event type names are identifiers and keep their lowercase dotted form; enum values inside payloads are UPPER_SNAKE (ADR-0080 §3). Each type is described as an entry of the OpenAPI `webhooks` section with `x-orcon-event { type, cloudEventsType, permission, stability, since }`, a named payload schema, descriptions and an example (ADR-0080 §6). Mapping from ADR-0009 in `docs/reference/public-events.md`. Payloads are thin (ids, status, timings, sanitized error summary). Execution output data only when `includeData` is requested and the principal holds `execution:read-data` (otherwise `dataHidden: true`), capped at 64 KiB with a link. Each event type declares the permission needed to receive it (e.g. `execution:read` on its project).

**Human-attention events** (semantics, triggering conditions, notification routing and escalation are defined by ADR-0073; this ADR defines only their public shape and delivery): `execution.awaiting_human` (an execution started waiting for a person), `execution.awaiting_human.escalated` (an unattended wait moved to a higher escalation level per ADR-0073), `execution.human_resolved` (a person continued, repeated or canceled). CloudEvents types `dev.orcon.execution.awaiting_human.v1`, `dev.orcon.execution.awaiting_human.escalated.v1`, `dev.orcon.execution.human_resolved.v1`. Delivered through SSE (§3, both the organization stream and the per-execution stream) and signed outbound webhooks (§4–§6) with the same guarantees as every other public event (same transaction, at-least-once, stable `webhook-id`). Payload is **redacted by default** per SPEC-004 R-AUD-09 (a): `attentionId`, organization, `executionId`, `projectId`, `flowId`, `flowVersion`, `nodeId`, flow and step names, `reason` (UPPER_SNAKE), `since`, deadline, `escalationLevel`, `availableActions`, and links to the REST operation and the editor view; for `execution.human_resolved` also `action` (`CONTINUE|REPEAT|CANCEL`) and the actor's id and kind. Never secrets (the SPEC-004 R-CRED-04 masking set also applies) and no protected execution data by default — `includeData` alone adds nothing to these types. The sent data (`sentData`) is present only when the project has enabled data inclusion in notifications (owner decision SPEC-004 N1: off by default; enabling requires `notification:manage` and `execution:read-data`; audited `notification.data_inclusion_changed`) **and** the receiving principal (SSE subscriber or the subscription's owning principal) holds `execution:read-data`; it is always masked (SPEC-004 R-CRED-04, ADR-0049) and capped at 4 KiB; otherwise `dataHidden: true`. Required permission to receive: `execution:read` on the project. Links in payloads never authorize an action by themselves (SPEC-004 R-AZ-13): acting requires normal authentication and the operation's permission; no secret-bearing one-click links exist.

**Operational alerts** (semantics in ADR-0073 §13): `connector.revoked` (CloudEvents `dev.orcon.connector.revoked.v1`), emitted per affected organization when a `CRITICAL` connector revocation affects installed packages (owner decision SPEC-003 N2). Payload: connector, revoked version, severity, reason, fixed version and affected flows (id, name, project; capped with a link), filtered to the projects the receiver can read; never secrets or execution data. Required permission to receive: read access to at least one affected project.

### 3. Real-time streaming (SSE)
- `GET /api/v1/events/stream` (`text/event-stream`), filters `types`, `projectId`, `flowId`; SSE `id` = `orconseq`; resume with `Last-Event-ID` within retention; an expired cursor yields `event: stream.reset`.
- `GET /api/v1/executions/{executionId}/events/stream`: full ADR-0009 catalog for one execution, including live-only events, for the editor and programs; requires `execution:read` (`execution:read-data` for data).
- Fan-out without a broker: each `api` process tails the logs with `LISTEN/NOTIFY` (`orcon_events`) plus 1 s polling (SQLite: in-process signal).
- Heartbeat every 15 s. Authorization checked at connect and per event using the cached evaluator of ADR-0041 §7; a revocation (epoch bump) closes affected streams within 1 s. Streams count against the `stream` rate class.
- No WebSocket in v1 (owner decision Q8).
- `GET /api/v1/flows/{flowId}/editing-sessions/stream` (experimental, permission `flow:read`): live-only events `presence.changed { sessions[] }` and `draft.saved { draftRevision, savedBy, savedAt }`; not public events, not persisted, not in the `webhooks` section; heartbeat every 15 s; no resume (clients re-list on reconnect); fan-out through `LISTEN/NOTIFY` on `orcon_flow_live` (SQLite: in-process signal); authorization at connect and per event.
- The per-execution stream also carries the ADR-0009 types `effect.preview_opened` and `effect.preview_resolved` (added by SPEC-014); they are not public catalog types.

### 4. Outbound webhooks
- `event_subscription(org_id, id, url, status: ACTIVE|PAUSED|DISABLED, is_data_included, purpose: GENERAL|ATTENTION, delivery_mode: EACH|GROUPED, body_format: STANDARD|SLACK|PAGERDUTY, maximum_concurrency, owner_principal_id?, created_by_principal_id?, revision, cursor_sequence_number, first_consecutive_failure_at?)`, with child tables `event_subscription_type(org_id, id, event_subscription_id, type)`, `event_subscription_project(org_id, id, event_subscription_id, project_id)` (no rows = every project the owner can read) and `event_subscription_secret(org_id, id, event_subscription_id, secret_ciphertext, created_at, expires_at?)` (two rows during rotation). The database stores the same values the API exposes (ADR-0015 §2). Managed with `event-subscription:manage`, except `purpose: ATTENTION` subscriptions, which are ADR-0073 notification channels: managing them requires `notification:manage` and emits `notification.channel_created|updated|deleted` (SPEC-004 Annex B). Secrets are encrypted under the organization key hierarchy (ADR-0042). Data-bearing subscriptions require that the owning principal holds `execution:read-data`; the check is repeated at delivery time; a subscription whose owner principal was deleted (`owner_principal_id` set to NULL) delivers without data.
- A dispatcher (one per subscription, leased; run as an `orcon_engine` discovery function across organizations, ADR-0047 §2) reads `public_event` after `cursor_sequence_number`, filters, and in one organization-scoped transaction inserts `webhook_delivery` rows and advances the cursor. Delivery workers in `worker` claim deliveries with lease and fencing (ADR-0013 §4), send through the egress client (ADR-0029 §8; private networks only if allowed by instance/organization policy), and record the outcome. A crash never loses an event.
- `webhook_delivery(org_id, id, event_subscription_id, public_event_sequence_number, public_event_id, attempt_count, status: PENDING|DELIVERING|SUCCEEDED|FAILED|DEAD, next_attempt_at, last_response_status, last_error, lease_owner, lease_epoch, lease_expires_at, created_at, finished_at)`; retention 30 days.
- No strict ordering (a failing event must not block later ones); payloads carry `orconseq` and `time`.
- **Attention subscriptions** (`purpose: ATTENTION`, ADR-0073 §2): receive the human-attention events and `connector.revoked` only when ADR-0073 routing names them; `deliveryMode` defaults to `GROUPED` (ADR-0073 §7 window and group key, group key included in the payload); their deliveries use a dedicated priority class in delivery workers so a backlog of other events never delays them. Other subscriptions to these types receive every event (`EACH`).
- **Body formats** (owner decision SPEC-001 N3; only for `purpose: ATTENTION`): `STANDARD` (CloudEvents, default); `SLACK` — a Slack incoming-webhook message (text and blocks with the redacted fields and the deep link; no interactive buttons, SPEC-004 N2); `PAGERDUTY` — a PagerDuty Events API v2 message: `trigger` on `execution.awaiting_human` / `.escalated` / `connector.revoked`, `resolve` when the group has no open request left, `dedup_key` = the ADR-0073 §7 group key so a burst opens one incident, routing key stored as an encrypted channel secret. All formats keep the Standard Webhooks headers (§5), go through the egress client and apply the same redaction.

### 5. Signing (Standard Webhooks)
`webhook-id` (event id, stable across retries), `webhook-timestamp`, `webhook-signature` = space-separated `v1,<base64(HMAC-SHA256(secret, id + "." + timestamp + "." + body))>`. Secrets in `whsec_` format. Rotation keeps two active secrets during an overlap (default 24 h) and sends both signatures. Same scheme as the "Standard Webhooks" ingress preset of ADR-0022 §5. SDKs include verification helpers.

### 6. Retries, dead letter, disabling
- Success = 2xx within 10 s. `410 Gone` disables the subscription. Otherwise exponential backoff with full jitter: ≈ 5 s, 30 s, 2 m, 10 m, 30 m, 1 h, 3 h, 6 h, 12 h, 24 h (≈ 2 days); `Retry-After` honoured up to 24 h.
- After the last attempt: `DEAD` (dead letter), event `webhook.delivery_dead`, visible via API; `POST /deliveries/{deliveryId}/redeliver` and `POST /event-subscriptions/{eventSubscriptionId}/replay?from=<time|seq>` (long-running) re-send within event retention.
- Continuous failure for 5 days (configurable) disables the subscription with `webhook.subscription_disabled`.
- Payload cap 256 KiB; larger events are sent thin with a link.
- At-least-once; receivers deduplicate by `webhook-id`; exactly-once is never claimed.

## Consequences
Real-time and push integrations with standard, verifiable signatures, isolated per organization, without a message broker; event types share the lint, the reference and the changelog with operations.

## Alternatives considered
Per-subscription outbox rows at write time (multiplies hot-path writes); WebSocket (no bidirectional need); custom signatures (Standard Webhooks is documented and matches the inbound preset); strict ordering (one bad event blocks all later ones); array columns for types and projects (rejected by ADR-0077: no foreign keys, no portable index).

Changes applied on 2026-10-12 by specifications the owner accepted together with this ADR; each entry names its source.

- **SPEC-006.** The public catalog gains `ai.budget.threshold`, `ai.budget.exceeded`, `ai.approval.requested`, `evaluation.run.finished` and `conversation.created`; enum values inside their payloads are UPPER_SNAKE and each type is described in the `webhooks` section with `x-orcon-event` (ADR-0080).
- **SPEC-014 (Amendment 5, carried by SPEC-005).** §3 gains the editing-session stream and the effect-preview events of the per-execution stream. Additive only (ADR-0054 §3): no existing operation, field, permission, MCP level or tool changes; semantics of test runs, pinned data and effect confirmation: ADR-0082 (SPEC-014).
- **SPEC-009 K19 (2026-10-13, owner decision).** §4 (`event_subscription.status`, `purpose`, `delivery_mode`, `body_format`; `webhook_delivery.status`): enumerated columns store the same UPPER_SNAKE values the API exposes (ADR-0015 §2 applies to every table); no adapter translates an enumerated value between the database and the API.
